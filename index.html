1. Pendahuluan: Apache Superset

Apache Superset adalah platform visualisasi data modern, cepat, dan tangguh yang digunakan untuk menampilkan data mentah maupun data olahan dalam bentuk dashboard dan grafik interaktif. Dengan dukungan konektivitas database yang luas melalui SQLAlchemy, Superset menjadi pilihan utama untuk operasional Business Intelligence (BI) yang fleksibel.

Eksplorasi & Query Data
  • SQL Lab: IDE query interaktif untuk merancang query SQL mentah langsung ke database.
  • Query to Dataset: Mengubah hasil analisis SQL Lab secara langsung menjadi dataset siap pakai.
  • Upload Data CSV: Kemampuan import file data lokal langsung ke penyimpanan database yang terkoneksi.
Akses & Pembagian Kolaborasi
  • Keamanan Granular: Pembagian dashboard, chart, dataset, dan koneksi berdasarkan User, Role, maupun Group.
  • Embedding & Sharing: Export chart menjadi embeddable iframe serta berbagi tautan dashboard berizin khusus.
  • Export Format: Mengunduh data hasil visualisasi ke CSV/Excel dan dashboard/chart utuh menjadi Image (PNG) atau PDF.

Pilihan Konsep Arsitektur

Berikut adalah dua rancangan konsep arsitektur yang dievaluasi untuk penerapan lokal (WSL / Komputer Pengembang) maupun deployment di server produksi.

Heavyweight Architecture

2. Konsep 1: Enterprise Full-Stack (Heavyweight)

Konsep 1 dirancang untuk ekosistem skala besar dengan kebutuhan sinkronisasi otomatis CDC (Change Data Capture), semantic layer tersentralisasi, dan caching asinkron.

Data Pipeline & Caching Flow (Konsep 1)
PostgreSQL (OLTP) Sumber Transaksional
➔
PeerDB (ETL/CDC) Staging via MinIO
➔
ClickHouse OLAP Store
➔
Cube.js Semantic Layer
➔
Superset (BI) Celery + Redis Cache
✓ Kelebihan & Justifikasi
  • Multi-BI Compatibility: Adanya Cube.js sebagai global semantic layer membantu agar definisi labeling data dan logika metrik terpusat dapat diakses bersamaan oleh Superset, PowerBI, Tableau, dll.
  • Otomatisasi CDC: PeerDB mempermudah sinkronisasi data dari database utama (OLTP) ke database analitis (OLAP ClickHouse) secara visual dengan minim penulisan kode ETL manual.
  • Caching yang Kuat: Redis dan Celery menangani query secara asinkron untuk membantu mengurangi risiko UI Superset mengalami hambatan/freeze.
✗ Kekurangan & Tantangan
  • Kerentanan Lonjakan Resource (Spikes): Pemakaian RAM dasar sebenarnya tidak terlalu besar, namun rawan kehabisan resource RAM & CPU secara ekstrem pada spesifikasi device lokal (seperti Intel i3-1115G4 dan RAM 8GB) ketika terjadi aktivitas bersamaan (proses ETL sinkronisasi berjalan saat user memuat dashboard).
  • Beban I/O Disk Tinggi: Pre-aggregations Cube.js memerlukan penyimpanan hasil agregasi ke database, meningkatkan operasi baca-tulis disk secara intensif.
  • Kompleksitas Pemeliharaan (Moving Parts): Banyaknya modul independen yang berjalan bersamaan (caching, queue, semantic layer, ETL) meningkatkan potensi kegagalan sistem dan membutuhkan monitoring yang ketat.

Lightweight Architecture

3. Konsep 2: Minimalist Setup (Lightweight)

Konsep 2 memotong seluruh komponen perantara untuk menghadirkan kecepatan setup, efisiensi resource laptop lokal, dan kemudahan pemeliharaan.

Data Pipeline & Caching Flow (Konsep 2)
Data Source (OLTP)
➔
Custom Script / Python Job Direct Bulk Load
➔
ClickHouse OLAP (Ready Table)
➔
Superset (BI) SQLite Local DB
✓ Kelebihan & Justifikasi
  • Sangat Ringan: Hanya membutuhkan 2 container utama setelah inisialisasi. Cenderung lebih stabil berjalan di device berspesifikasi rendah dengan risiko crash yang lebih rendah.
  • Mudah Di-maintain: Lebih sedikit bagian bergerak (moving parts) membantu meminimalkan potensi kegagalan sistem.
  • Query Cepat: ClickHouse melakukan kompresi data kolom secara agresif, membantu mempercepat eksekusi query analitis dibanding database relasional biasa.
✗ Kerentanan Sistem Nyata
  • Database SQLite Locked: Menggunakan database SQLite lokal bawaan Superset. Jika beberapa user mengakses/mengedit dashboard bersamaan, transaksi SQL rentan terblokir (locked).
  • UI Freeze & Timeout: Tanpa Redis/Celery, query berat dari ClickHouse dieksekusi secara sinkron. Halaman visualisasi berisiko membeku dan rentan memicu Gunicorn 504 Timeout.
  • Beban ClickHouse Berulang: Setiap filter dashboard memicu query langsung baru ke ClickHouse dari awal.
Daftar Container Docker - Konsep 2 (Minimalis)

Container Utama (Wajib)

superset-app Web UI utama (SQLite local metadata)
clickhouse-server Engine database OLAP analitis

Container Pendukung (Opsional)

postgres Metadata database (pengganti SQLite)

Catatan Keamanan & Batasan Fitur
Tanpa adanya background worker (Celery) pada Konsep 2, fitur Alerts & Reports (pengiriman grafik via email/Slack otomatis secara terjadwal) tidak dapat berfungsi sama sekali karena memerlukan penjadwalan asinkron di latar belakang.

5. Perbandingan: Apache Superset vs Power BI Desktop

Berikut adalah analisis komprehensif antara Apache Superset dan Microsoft Power BI Desktop untuk kebutuhan visualisasi data analitis dari sumber data (source):

Kriteria Evaluasi Apache Superset Power BI Desktop
Akses & Platform Berbasis Web (Cloud-native). Dapat diakses dari sistem operasi apa pun melalui web browser. Aplikasi Desktop khusus Windows. Pengguna macOS/Linux memerlukan VM atau Remote Desktop.
Konektivitas Sumber Data Koneksi langsung via SQLAlchemy. Relatif mudah dikonfigurasi dan ramah terhadap query besar. Membutuhkan driver ODBC khusus atau konektor bawaan di Windows.
Metode Pengambilan Data Selalu melakukan query langsung (Direct Query) ke sumber data (source) secara native. Mendukung Import Mode (data diimpor ke RAM lokal) atau DirectQuery (query langsung ke sumber data).
Semantic Layer Bersifat tipis (ringan). Untuk logika metrik bisnis yang rumit biasanya dipasangkan dengan Cube.js atau dbt. Sangat kaya dan matang. Menggunakan bahasa DAX dan pemodelan Tabular untuk relasi data yang kompleks secara bawaan.
Beban Device Lokal Sangat ringan di sisi klien (device lokal hanya menjalankan peramban/browser). Cenderung berat jika menggunakan Import Mode karena memproses data di RAM device lokal.
Pembaruan Data & File Sharing Memungkinkan akses mandiri karena dataset utama sudah terpusat dan terupdate otomatis di web tanpa perlu menunggu kiriman berkas terbaru, dengan tetap mendukung unggah berkas Excel tambahan jika diperlukan. Jika bergantung pada berkas Excel lokal, berkas perlu diperbarui berkala (baik meminta berkas baru atau menunggu email otomatis) sehingga alur kerjanya kurang praktis.
Kolaborasi & Lisensi Open-source (Gratis). Berbagi dashboard ke pengguna lain tidak memerlukan biaya lisensi tambahan. Pembuatan laporan lokal gratis, tetapi berbagi/kolaborasi via web service membutuhkan lisensi Pro/Premium per user.
Kapan memilih Apache Superset?
  • Membutuhkan platform visualisasi berbasis web terpusat agar seluruh pengguna dapat mengakses data terupdate secara mandiri tanpa perlu menunggu kiriman file berkala.
  • Ingin menghindari biaya lisensi per pengguna untuk kebutuhan kolaborasi dan berbagi dashboard.
  • Lebih menyukai analisis data berbasis kueri SQL langsung ke sumber data.
  • Memiliki infrastruktur server/Docker terpisah agar pemrosesan data tidak membebani device lokal.
Kapan memilih Power BI Desktop?
  • Tim sudah terintegrasi dalam ekosistem Microsoft dan pengguna lebih terbiasa menggunakan Excel atau formula DAX.
  • Membutuhkan pemodelan data lokal yang kompleks dan relasi antar tabel yang rumit sebelum laporan dibagikan.
  • Memiliki spesifikasi device lokal yang memadai jika ingin menggunakan Import Mode untuk data berukuran besar guna meminimalkan risiko lambat.

6. Rekomendasi & Solusi Jalan Tengah

Berdasarkan realitas keterbatasan infrastruktur komputer lokal, arsitektur terbaik adalah menerapkan Konsep 2 yang dioptimalkan (Solusi Hybrid). Kita meminimalkan container tetapi menutup lubang kelemahan fatal SQLite dan query sinkron.

A. Migrasi SQLite ke PostgreSQL (Metadata Superset)

Dengan mengubah database internal Superset dari SQLite bawaan menjadi database PostgreSQL mandiri (dapat berupa kontainer Docker Postgres kecil tambahan), kita membantu memitigasi tiga kendala operasional utama:

  • Mengurangi Risiko Database Locked: PostgreSQL menangani transaksi simultan dengan baik, membantu meminimalkan risiko hambatan locking saat berkolaborasi mendesain dashboard.
  • Keamanan Data Metadata: PostgreSQL menggunakan mekanisme Write-Ahead Logging (WAL). Jika server atau WSL crash akibat beban kerja tinggi, metadata Superset (dashboard, grafik, role) berpotensi lebih terlindungi dari kerusakan data (korup).
  • Siap Skala Up: Membantu memudahkan integrasi caching Redis dan celery worker di kemudian hari jika dibutuhkan tanpa perlu memigrasi data dari SQLite.
B. Optimalisasi Layar Dataset Superset (Pengganti Cube.js)

Tanpa Cube.js, standarisasi labeling dipindahkan langsung ke dalam menu manajemen Dataset di Apache Superset. Superset menyediakan antarmuka internal yang kuat:

  • Labeling Kolom: Kolom database analitis yang kaku seperti dtl_tr_id dapat dideklarasikan dengan label manusiawi "ID Detail Transaksi". Pengguna awam cukup melakukan drag-and-drop label ramah tersebut.
  • Datetime Format: Kunci format waktu standardisasi (misalnya YYYY-MM-DD HH:mm:ss) di tingkat dataset agar tidak terjadi perbedaan representasi zona waktu di tiap grafik.
  • Calculated Columns: Logika bisnis (misal: Harga * Jumlah * (1 - Diskon)) dapat ditulis langsung sebagai kolom kalkulasi sekali saja menggunakan sintaks SQL ClickHouse, siap dipakai oleh seluruh visualisasi turunan.
C. Manajemen Siklus Data di ClickHouse (DML & Partisi)

ClickHouse adalah database columnar yang bersifat append-only. Operasi DML UPDATE atau DELETE standar akan sangat lambat dan memakan resource. Berikut mitigasi performanya:

  • ReplacingMergeTree Engine: Gunakan engine tabel ini untuk mengatasi data transaksional yang sering berubah status. ClickHouse dirancang untuk menyaring data lama dan menyisakan data dengan versi terbaru secara berkala di latar belakang berdasarkan primary key.
  • Partisi Tabel: Selalu partisi data tabel ClickHouse (misal per bulan/tahun). Partisi yang tepat membantu mengurangi kemungkinan terjadinya kueri memindai seluruh tabel data (full-table scan) saat filter dashboard diubah, sehingga membantu menghemat penggunaan CPU ClickHouse.
