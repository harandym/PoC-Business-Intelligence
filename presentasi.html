Pengenalan

Pendahuluan: Apache Superset

Apache Superset adalah platform visualisasi data modern, cepat, dan tangguh untuk menampilkan visualisasi interaktif dari data mentah/olahan. Mendukung konektivitas luas via SQLAlchemy.

Eksplorasi & Query Data
  • SQL Lab: IDE query interaktif terintegrasi untuk merancang SQL.
  • Query to Dataset: Hasil query SQL langsung diubah menjadi dataset siap pakai.
  • Upload Data: Kemampuan import file data lokal (CSV) langsung ke DB target.
Kolaborasi & Aksesibilitas
  • Keamanan Granular: Izin akses spesifik per User, Role, Group, maupun Dataset.
  • Sharing & Embedding: Integrasi grafik via iframe serta export dashboard.
  • Export Multi-Format: Mendukung export ke CSV, Excel, Image PNG, dan PDF.
Pilihan Desain

Dua Opsi Arsitektur Deployment

Evaluasi berfokus pada dua skenario arsitektur dengan karakteristik beban dan fungsionalitas yang berbeda:

Konsep 1: Enterprise Full-Stack

Arsitektur heavyweight terpadu yang mengintegrasikan otomatisasi CDC (Change Data Capture), global semantic layer, antrean tugas asinkron, dan caching berlapis.

  • Ideal untuk volume data besar & CDC semi-instan
  • Kompatibilitas Multi-BI via semantic layer terpusat (Cube)
  • Menghindari pembekuan UI dengan antrean Celery
Konsep 2: Minimalist Setup

Arsitektur minimalis & efisien yang memotong seluruh middleware demi kemudahan pemeliharaan dan penghematan RAM pada server target.

  • Instalasi sangat instan & minim bagian bergerak
  • Sangat ringan untuk uji coba/PoC lokal (RAM idle ~1GB)
  • Menggunakan query langsung ke columnar store ClickHouse
Konsep 1: Enterprise

Data Pipeline & Caching (Enterprise Full-Stack)

Arsitektur komprehensif dari hulu ke hilir untuk meminimalkan beban di database transaksional (OLTP):

PostgreSQL (OLTP) Sumber Transaksional
→
PeerDB (CDC) Staging via MinIO
→
ClickHouse OLAP Columnar Store
→
Cube.js Semantic & Pre-Agg
→
Superset (BI) Render Dashboard
  • CDC Otomatis: Replikasi real-time dari PostgreSQL OLTP ke ClickHouse OLAP menggunakan CDC PeerDB.
  • Cube.js Semantic Layer: Mendefinisikan metrik bisnis satu kali untuk diakses oleh berbagai tool BI.
  • Asynchronous Celery Workers: Menghindari timeout di UI dengan memproses kueri berat di latar belakang.
Konsep 2: Minimalis

Data Pipeline & Caching (Minimalist Setup)

Arsitektur minimalis yang memangkas komponen perantara untuk menghemat memori komputer lokal:

Data Source (OLTP) Sumber Transaksi
→
Custom Python Script Direct Bulk Load
→
ClickHouse OLAP Store (Flat Table)
→
Superset (BI) SQLite Local Metadata
  • ETL Sederhana: Menggunakan script Python terjadwal secara berkala untuk memindahkan data.
  • Direct Querying: Superset langsung menembak ClickHouse untuk memuat visualisasi grafik.
  • Keterbatasan Fitur: Tanpa Celery workers, fitur Alerts & Reports terjadwal tidak dapat aktif.

Strategi Deployment

Rekomendasi A: Strategi Fase PoC & Produksi

Mengapa Konsep 1 Ditunda di Fase PoC Lokal?

Spesifikasi hardware lokal pengujian (RAM 8 GB, CPU i3) sengaja difungsikan sebagai stress test untuk memetakan batasan sistem.

  • Beban Idle Berlebih: Konsep 1 dengan 14 kontainer memakan >50% kapasitas RAM lokal bahkan sebelum memproses data.
  • Risiko Crash: Sinkronisasi PeerDB secara konstan bersamaan query analitis terbukti memicu kegagalan resource di mesin lokal.
Konsep 1 Sebagai Target Produksi Utama

Meskipun ditunda untuk pengujian lokal, Konsep 1 tetap menjadi rekomendasi final target produksi pada server Linux/Kubernetes dedicatd.

  • Solusi Comprehensive: Sangat ideal jika internal organisasi belum memiliki pipeline ETL, CDC, maupun global semantic layer.
  • CDC Otomatis: Replikasi data dari OLTP PostgreSQL ke ClickHouse berjalan mulus tanpa coding manual ETL.
Optimasi

Rekomendasi B: Solusi Hybrid Pengujian PoC

Agar pengujian PoC lokal tetap stabil dan terhindar dari keterbatasan database SQLite bawaan, berikut langkah optimasi hybrid:

B.1 Migrasi Metadata ke PostgreSQL

Ganti database internal Superset (SQLite) dengan container PostgreSQL mandiri:

  • Anti-Locking: Mencegah kendala "Database Locked" saat multi-user mengedit dashboard.
  • Durabilitas: Melindungi metadata dari kerusakan data jika server/Docker terhenti paksa.
B.2 Optimasi Dataset & ClickHouse

Konfigurasi visualisasi & siklus data langsung di level dataset dan ClickHouse Engine:

  • ReplacingMergeTree Engine: Mengatasi data transaksi yang sering berubah status (DML update).
  • Calculated Columns: Tulis formula logika bisnis (misal total harga) sekali saja di SQL Dataset.
  • Dataset Labeling: Mengubah field SQL kaku menjadi label ramah pengguna (contoh: dtl_tr_id → ID Transaksi).
